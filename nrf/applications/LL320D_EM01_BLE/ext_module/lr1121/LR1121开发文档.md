# LR1121 Modem-E 从 0 到 1 开发指南

本文档面向 `LL320D_EM01_BLE` 后续研发人员，记录 LR1121 Modem-E 在 nRF54L15 上从硬件连接、驱动移植、固件准备到 LoRaWAN 业务调用的完整路径。本文档对应当前工程中的实现；修改硬件、NCS 版本或 Modem-E 固件版本后，应重新核对引脚、时序和 API 兼容性。

## 1. 方案概览

本项目使用 **LR1121 Modem-E**，而不是在 nRF54L15 上移植完整 LoRaWAN MAC。LoRaWAN 协议栈运行在 LR1121 的 Modem-E 固件中，nRF54L15 通过 SPI 发送命令并轮询事件。

软件分层如下：

```text
业务/4G命令
    -> src/my_lora.c                 LoRa 线程、状态机、周期上行、下行处理
    -> ext_module/lr1121/api         本项目的 API 封装
    -> modemE_driver/src             Semtech Modem-E v2.0.0 驱动
    -> port/modem_e_hal_nrf54l15.c   Zephyr SPI/GPIO/延时 HAL
    -> LR1121 Modem-E v2.1.0 固件
```

当前已实现的目标流程是：硬件复位、读取版本、LoRaWAN OTAA 配置与入网、周期上行、事件轮询、下行数据读取和 Class A/B/C 设置接口。

## 3. 硬件连接

当前 overlay 使用 `spi20`，连接关系如下。所有数字信号使用 3.3 V 电平，必须共地。

| LR1121 | nRF54L15 | 用途 |
| --- | --- | --- |
| SCK | P2.01 | SPI 时钟 |
| MOSI/SDO | P2.02 | nRF54L15 -> LR1121 |
| MISO/SDI | P2.04 | LR1121 -> nRF54L15 |
| NSS/CS | P2.05 | 低有效片选 |
| LR_NRESET | P2.03 | 低有效硬复位 |
| BUSY | P2.00 | LR1121 忙状态输出 |
| GND | GND | 共地 |
| +3V3 | +3V3 | 评估板未独立供电时使用 |

注意：

1. `BUSY` 不是 DIO0/DIO9。本实现采用 `modem_e_get_event()` 轮询，不需要 DIO9 IRQ。
2. 若评估板已由 USB 或其他电源供电，不要并联不明的 3.3 V 电源，只连接 GND 和数字信号。
3. LoRa 天线接对应 Region 的 LoRa SMA 口，不要误接 2.4 GHz 口。
4. P2.05 原用于环境传感器电源控制，当前已让出给 NSS；`uart20` 也因 `spi20` 资源冲突而禁用。

## 4. 驱动移植步骤

### 4.1 复制和选择 Semtech 源文件

将官方仓库固定到一个可追溯版本，复制到 `ext_module/lr1121/modemE_driver/`。本工程只编译 Modem-E LoRaWAN 所需文件：

```text
modem_e_modem.c
modem_e_lorawan.c
modem_e_system.c
```

不要只添加 `modem_e_system.c`；LoRaWAN 入网、发送、事件和下行接口分别依赖 `modem_e_modem.c` 与 `modem_e_lorawan.c`。

### 4.2 Devicetree 和 Kconfig

参考当前文件：

- `boards/nrf54l15dk_nrf54l15_cpuapp.overlay`
- `dts/bindings/lora/semtech,lr1121-modem-e.yaml`
- `prj.conf` 中的 `CONFIG_SPI=y`

必须完成以下配置：

1. 为 `spi20` 配置 SCK/MOSI/MISO pinctrl 和 `cs-gpios`。
2. 创建 `lr1121@0` SPI 子节点，设置 `spi-max-frequency = <8000000>`。
3. 提供 `busy-gpios` 和 `reset-gpios` 属性。
4. 为 SPI 从设备添加 compatible binding。缺少 binding 时，`SPI_DT_SPEC_GET()` 生成的 `spi_max_frequency` 等属性会缺失并导致编译失败。
5. 处理复用冲突：禁用 `uart20`，释放 P2.05 给 LR1121 NSS，并避免业务代码对 disabled 设备使用 `DEVICE_DT_GET()`。

### 4.3 编写板级 HAL

`port/modem_e_hal_nrf54l15.c` 实现 Semtech HAL，核心要求如下：

- 使用 `spi_transceive_dt()` 进行 SPI 事务。
- 命令前后按 Modem-E 规定等待 BUSY 电平。
- 复位脚输出低有效复位脉冲。
- 唤醒时产生 NSS 脉冲。
- 校验命令响应的 status/data CRC。
- 复位释放后轮询 `GET_EVENT`，确认收到明确的 reset event 后再继续配置。

建议先只完成“复位 -> 读取 Modem-E 版本”，确认 SPI、BUSY、RESET 和 CRC 均正常，再加入 OTAA。

### 4.4 应用层接入

`api/lr1121_lora_api.h/.c` 隔离业务代码和 Semtech 原始 API；`src/my_lora.c` 仅由一个 LoRa 线程拥有 Modem-E，其他模块通过工程消息机制投递 `MY_MSG_LORA_ENABLE` / `MY_MSG_LORA_DISABLE`。

当前行为：

- `my_lora_init()` 只创建线程，默认状态为 OFF，不立即复位或入网。
- 启用后执行 RESET -> 读取版本 -> 配置 Region/OTAA -> Join。
- 线程每 100 ms 轮询事件；Join 失败按 30 s 重试。
- 入网后按配置周期上行，并处理 `TX_DONE`、`DOWN_DATA`、区域占空比等事件。

## 5. LR1121 固件获取和烧录

### 5.1 获取固件

从 Semtech 官方 `SWTL001` Wiki 进入与 **LR1121 Modem-E v2.1.0** 对应的发布包。下载前核对：芯片型号是 LR1121、目标是 Modem-E、版本与驱动兼容，而不是 LR1121 裸 radio 固件或 LR1110 固件。驱动仓库 README 已明确当前驱动兼容 LR1121 Modem-E v2.1.0。

下载后保留原始压缩包、版本号和校验值，并记录实际烧入的文件名。不要把固件二进制提交到应用源码目录，除非项目另有制品管理要求。

### 5.2 烧录前检查

1. 断开 nRF54L15 对 LR1121 的 3.3 V 供电并确认评估板供电方式，避免电源并联。
2. 连接评估板官方升级接口（通常为 USB/UART/板载调试器，具体以 `SWTL001` Wiki 和评估板说明为准）。
3. 记录原固件版本；应用启动后可通过 `app lora status` 或 `lr1121_lora_get_version()` 读取版本。
4. 确认天线、Region 和实验室射频许可条件；固件升级完成前不要进行长时间发射测试。

### 5.3 烧录步骤

具体升级工具和命令随发布包及评估板版本变化，按官方包内的升级器/脚本执行：

1. 安装发布包要求的 USB 驱动和升级工具。
2. 将 LR1121 评估板置于官方 DFU/升级模式并识别端口。
3. 在升级器中选择 LR1121 Modem-E v2.1.0 对应的固件镜像，先执行读取/备份（若工具支持），再执行擦除和烧录。
4. 等待校验通过，退出 DFU 并重新上电。
5. 通过 `GET_VERSION`、reset event 和 `app lora status` 验证版本；若版本不匹配，先停止应用层 Join 排查固件选择和升级模式。

> 不同评估板的 DFU 入口、端口号和命令行参数并不统一，因此本文不硬编码某一块板的命令。以 `SWTL001` Wiki、发布包 README 和 `AN1200_92` 为准；没有官方升级器时不要直接用 nRF Connect Programmer 将 Modem-E 镜像写入 nRF54L15。

## 6. 编译、烧录和首次验证

在 NCS v3.2.1 工具链下构建示例：

```powershell
$env:Path = 'D:\ncs\toolchains\66cdf9b75e\opt\bin;' + $env:Path
& 'D:\ncs\toolchains\66cdf9b75e\opt\bin\ninja.exe' -C build
```

成功产物为 `build/merged.hex`。使用项目既有的 nRF54L15 烧录流程写入主控；烧录后打开 RTT Shell。

推荐验证顺序：

1. `app lora status`：确认 LR1121 能识别、版本可读、Join 状态为未入网。
2. `LTE+LORA=1`：确认线程启动、复位和版本读取成功。
3. 填入真实 Region/DevEUI/JoinEUI/AppKey 后等待 Join 成功。
4. 手动触发一次上行或等待周期上行：发送 `src/my_lora.c` 中的 `s_lora_uplink_payload` 正式业务载荷，检查网络服务器是否收到。
5. 从网络服务器下发匹配 FPort 的数据，确认 RTT 输出下行长度、端口和 payload。
6. `LTE+LORA=0`：确认退出网络并停止轮询。

当前 `MY_LORA_USE_TEST_CONFIG` 默认开启，使用 `src/my_lora.c` 中保存的研发测试配置；关闭该宏后为全零占位配置，只能做硬件/版本检测。真实密钥不得提交到公共仓库或文档正文。

## 7. LoRaWAN 功能使用

### 7.1 OTAA 入网

测试数据统一放在 `LL320D_EM01_BLE/src/my_lora.c` 顶部的 `s_lora_config` 配置区，并由 `MY_LORA_USE_TEST_CONFIG` 宏控制。研发联调时只修改该处或切换宏，不要修改 `ext_module/lr1121/api` 或 Semtech 驱动。需要配置：Region、DevEUI、JoinEUI、AppKey、上行 FPort、下行 FPort 和发送周期。Region 必须与网关/网络服务器一致，EUI 和 AppKey 按 Modem-E API 要求的字节序填写。

当 `MY_LORA_USE_TEST_CONFIG` 为 `1` 时，代码使用 `my_lora.c` 中已保留的研发测试 DevEUI、JoinEUI 和 AppKey，可直接进行测试网络 Join；改为 `0` 后使用全零量产占位配置。测试密钥仅限授权测试网络使用，禁止复制到公共仓库或量产固件。

业务调用路径为：

```c
lr1121_lora_configure_otaa(dev_eui, join_eui, app_key);
lr1121_lora_join();
lr1121_lora_get_event(&event);
```

只有收到 `MODEM_E_LORAWAN_EVENT_JOINED` 后才允许发送应用数据。

### 7.2 上行

应用层使用：

```c
int my_lora_send_payload(const uint8_t *payload, uint8_t payload_length);
```

限制：payload 长度为 1 到 `MY_LORA_MAX_PAYLOAD_LENGTH`（当前为 70 字节），必须已识别 LR1121 且已 Join。底层对应 `lr1121_lora_request_tx(fport, uplink_type, payload, length)`；确认/非确认上行由 `modem_e_uplink_type_t` 选择。

### 7.3 下行

收到 `MODEM_E_LORAWAN_EVENT_DOWN_DATA` 后：

1. 使用 `lr1121_lora_get_downlink_data_size()` 读取长度和剩余条数。
2. 使用 `lr1121_lora_get_downlink_data()` 读取 payload。
3. 使用 `lr1121_lora_get_downlink_metadata()` 读取 FPort、RSSI/SNR 等元数据。
4. 先按约定 FPort 过滤，再交给业务协议解析；Orange/KKS payload 格式尚未在本工程固定，不能自行定义兼容格式。

### 7.4 Class、链路检查和版本

API 已封装以下能力：

- `lr1121_lora_get_class()` / `lr1121_lora_set_class()`：读取或设置 Class A/B/C。
- `lr1121_lora_get_link_check_data()`：读取最近一次 Link Check 的 margin 和网关数量。
- `lr1121_lora_get_version()`：读取 Modem-E 固件版本。
- `lr1121_lora_get_lorawan_version()`：读取 LoRaWAN/RP002 版本。
- `lr1121_lora_leave_network()`：退出当前网络并停止进行中的 Join。

除非网络策略明确要求，不要在电池设备上默认使用 Class C；它会显著增加接收功耗。

## 8. 常用命令和错误码

| 命令 | 作用 |
| --- | --- |
| `app lora status` | 查看识别、凭证和 Join 状态 |
| `LTE+LORA=1` | 异步启动 LoRa 服务 |
| `LTE+LORA=0` | 停止服务并退出网络 |
| 周期上行/业务触发上行 | 已入网后发送 `src/my_lora.c` 中的 `s_lora_uplink_payload` |

上行接口常见返回值：`-ENODEV` 未识别 LR1121，`-EACCES` 凭证全零，`-EAGAIN` 尚未 Join，`-EBUSY` Modem-E 忙。

## 9. 排障顺序

| 现象 | 优先检查 |
| --- | --- |
| 编译找不到 `spi_max_frequency` | `lr1121@0` 的 compatible 和 binding 是否匹配 |
| `__device_dts_ord_xxx` | 是否引用了被 overlay 禁用的 `uart20` 或其他设备 |
| BUSY 超时 | 3.3 V、共地、BUSY 方向、P2.00 接线和评估板供电 |
| reset event 超时 | P2.03 极性、固件是否为 Modem-E、复位释放后的等待时间 |
| CRC 错误 | SPI SCK/MOSI/MISO/NSS 对应关系、SPI 模式、线长和电平 |
| 能读版本但 Join 失败 | Region、EUI/AppKey 字节序、网关覆盖、网络服务器配置 |
| 能 Join 但无上行 | FPort、payload 长度、区域占空比、网关和网络服务器日志 |
| 下行未到业务层 | FPort 过滤、下行队列长度和 `DOWN_DATA` 事件处理 |

先通过“读版本”闭环，再逐级加入 Join、上行、下行和低功耗。任何改动后都应重新记录：主控固件版本、Modem-E 固件版本、Region、硬件接线和测试结果。

## 10. 本次移植验证记录

已使用 NCS v3.2.1 工具链完成构建，生成 `build/merged.hex`。当前记录的资源占用为：FLASH 40848 B / 54 KB（73.87%），RAM 22368 B / 188 KB（11.62%）。工程仍有少量既有编译警告，但 LoRa 集成没有编译或链接错误。

本次移植中确认的典型问题：

1. `lr1121@0` 缺少 compatible binding 会导致 `SPI_DT_SPEC_GET()` 找不到 `spi-max-frequency`、`duplex`、`frame-format` 等属性；必须保留 `semtech,lr1121-modem-e.yaml`。
2. Modem-E 事件类型和 `modem_e_get_event()` 的声明来自 `modem_e_modem.h`；应用层统一通过 `lr1121_lora_api.h` 使用，避免分散底层头文件依赖。
3. 禁用 `uart20` 后，任何 `DEVICE_DT_GET()` 直接引用都会产生 `__device_dts_ord_xxx` 错误；禁用设备必须使用 `DEVICE_DT_GET_OR_NULL()`，并停止对应初始化调用。

首次实机验证必须依次确认：读取 Modem-E 版本、收到 reset event、使用测试配置 OTAA Join、收到正式业务上行、验证指定 FPort 下行，再验证关闭流程。
